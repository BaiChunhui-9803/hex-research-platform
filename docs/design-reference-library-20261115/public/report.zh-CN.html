清爽游戏式网页：参考库与复现方案

核验日期：2026年11月15日。对象是已有的HEX统一平台，重点是字体、布局、视觉层次和交互组织。

建议采用“展示页有游戏气质、工作台以画面为中心、实验页保持数据清楚”的组合。 CoG 2027适合作为入口与品牌参考；Lichess、Excalidraw、Sandspiel更适合实际操作区域；Elevator Saga最接近你提出的“问题＋方法”结构。没有必要为此更换已经实现的问题、方法和API架构。

1. 实际获取了什么

本次实测22个可用页面，对应20个关联GitHub项目。保存了页面截图、计算样式中的字体声明、加载字库、源码提交标识、布局源码样本和许可文件。共保存46份选定布局／字体样式源码样本，来自19个项目；tldraw只保留许可和源文件链接，没有下载其布局代码。

另有6个候选未计入有效参考：Hextris、Vue Minesweeper在本机出现浏览器连接或证书错误页；Gridland未取得可用内容；Untrusted与采集脚本不兼容；The Password Game、Jstris遇到访问验证。它们的失败记录保留在审计数据中，没有用搜索摘要冒充页面实测。

参考库不等于22套可以直接发布的完整模板。 它包含实际页面、对应源文件样本和复现配方；复杂项目没有在本机全部构建。以下三者分别标注：

  1. 页面观察：实际渲染出的布局、字号与CSS字体声明。
  2. 源码核验：固定提交中的样式、变量、入口与许可；不保证线上部署与该提交完全一致。
  3. 独立复现：根据归纳出的布局原则制作的三个可运行原型，复用现有HEX问题插件，没有导入参考项目的界面代码。

首屏与工作状态也分开记录。例如shapez追加观察到主菜单；Little Alchemy 2进入了元素操作界面；Squoosh最初捕获的是入口，源码另外覆盖压缩工作区。Lichess与Lidraughts、Flexbox Froggy与Grid Garden分别属于相关设计家族，项目数量不冒充独立风格数量。

2. CoG 2027：应当借鉴的具体内容

IEEE CoG 2027官网的CSS与浏览器实测相互印证：

角色 原站字体／参数 对HEX的建议
正文、导航、按钮 Inter，系统无衬线回退 用于界面主体，保持字重与字号层次
标签、数字、倒计时 JetBrains Mono 用于种子、时间、评分和短标签；表格数字等宽对齐
大标题 Noto Serif JP，Georgia回退 仅用于入口页标题；工作区使用更紧凑的无衬线标题
内容宽度 .container最大1200px，左右有内边距 用于入口与介绍页；工作台可更宽
主色 深蓝、暖红，少量金色与青色 以一个主强调色组织主按钮，地图线路／阵营色单独保留
装饰 细网格、少量像素与方形边界 作为低对比背景或局部品牌元素
首屏 100vh展示区，大标题使用clamp 只用于展示入口，操作页不保留大首屏

它的游戏感来自字体角色分工、主题色、细网格和局部装饰，不是整页使用像素字体。大段正文、参数表单和实验数据仍然采用清晰字体。这一点比单纯“换成游戏字体”更适合研究平台。

原站样式中的颜色和字号已作为观察参数记录；没有取得其Logo、美术或整站代码再利用授权，因此示例采用自己的HEX标识与独立CSS实现。

3. 22个参考对象分别怎样使用

完整对照表在本文附录与可筛选图库中。这里给出优先顺序：

用途 优先参考 主要借鉴内容
入口和问题选择 CoG 2027、PyChess、2048 清晰入口、适量品牌、大标题与核心行动
实际游戏工作区 Lichess、Excalidraw、Sandspiel、SVGOMG 画面优先、轻量工具条、侧栏／抽屉
地图与场景参数 Red Blob Games Mapgen4 参数、种子、即时画面之间的联系
问题与方法并列 Elevator Saga、Flexbox Froggy、CSS Diner 目标、输入、执行、可见结果的闭环
统计和聚焦 Monkeytype、keybr 字体分工、少量关键反馈、主题集中管理
局部工具布局 Piskel、JS Paint 稳定的工具位置和工作区分工；不照搬密集边框或微小文字

这些项目分成六类布局，而不是一个万能模板：

  • 展示入口：大标题、行动按钮、问题卡片，适合平台首页。
  • 单焦点任务：一个核心任务与少量反馈，适合简洁演示或聚焦模式。
  • 画布工作台：主画布、工具条、按需面板，最适合地铁与小队的实际操作。
  • 画面＋分析器：主画面与方法／轨迹分析并列，适合研究模式。
  • 任务＋方法输入：说明、算法输入和结果相互对应，适合教学和算法交流。
  • 大厅／目录：多个问题或关卡入口，适合新增问题后的发现与选择。

4. 字体方案：三种角色即可

建议默认组合为：

角色 建议字体 使用范围
界面主体 Inter＋中文系统回退 导航、按钮、设置、说明
数据与代码 JetBrains Mono 时间、种子、指标、代码和短标识
展示性标题 可选Noto Serif JP 首页HEX Research标题；不扩散到每个面板

如果希望更圆润，可另考虑2048线上所用Rubik；更轻松的学习游戏可用Fredoka One一类字体点缀品牌。这些是候选方向，不建议同时堆到同一页面。

本次已经从官方字体项目保存Inter与JetBrains Mono网页字体及OFL许可，并保存Noto Serif JP的演示标题子集。原型不依赖Google字体CDN。Noto子集只含“HEX Research Games”演示文字，正式使用需按实际标题生成子集或采用完整字体。

另外，font-family声明不等于实际每个字形都由第一项字体绘制。审计分别保留声明、已加载FontFace和字体网络资源；未使用CDP逐字形验证，也不把项目中的GameFont别名直接认作某种具体字库。

建议字号与间距：

内容 建议范围
正文／主要说明 14—16px，行高1.5—1.65
按钮／表单 13—14px，足够的点击面积
次要标签 11—12px；核心操作避免缩成微小文字
工作区标题 18—24px
首页标题 48—96px，以clamp响应式控制
数字 16—22px，font-variant-numeric: tabular-nums
间距 优先8px尺度，必要时4px微调
分组方式 留白、对齐、轻边界；少量阴影

英文界面与中文文档可以使用不同字体回退，但应保留同一套字号角色，避免混用十几种字号和过多字距。

5. 如何映射到现有平台

5.1 Problems：把展示与操作分成两个状态

入口页可保留CoG式氛围：一个主标题、一段解释、两个问题入口、少量平台信息。进入具体问题后，收起展示性内容，让画面、控制与状态进入首屏。

当前平台的导航、问题选择、场景工具栏、标题、指标和操作区是连续竖排的。后续正式改版应优先压缩这些层级，把“开始、暂停、步进”放到无需寻找的位置，而不是只更换颜色。

5.2 Workspace：画面为主，方法为辅

建议桌面使用：

紧凑顶栏：品牌 / Problems / Methods / Experiments
场景工具栏：问题 / 场景 / 种子 / 重置
主工作区：弹性画面                    方法与参数检查器
          问题专属轻工具条            默认只保留必要设置
          地铁SVG或小队Canvas         详细解释按需展开
底部控制：开始 / 暂停 / 步进 / 时间 / 倍速

主工作区宽度分配可以从“弹性画面＋约280px检查器”开始；窄屏时检查器转为抽屉或下方区域。不要把地图强制缩进一个很窄的卡片，也不要用多个厚重面板重复包裹画面。

游戏内部语义色单独保留：地铁A/B/C线路色、阵营色、警报色，不应都跟随页面主题的单一accent颜色变化。

5.3 Methods：可扫描的库，而不是操作页长说明

方法页负责解释共享优化器、专用策略、适用问题和参数。工作台只展示当前方法、关键参数、运行／接管按钮及必要提示。保留已有兼容性判断，通过协议与能力显示可用性，不以颜色或名字猜测算法能否用于某问题。

5.4 Experiments：数据优先

用清楚的表格、少量筛选和实际结果呈现比较。数字等宽、单位明确，单种子的标准差不要伪装成0。一次运行的条件与结果放在一起，详细轨迹再展开。不需要把每项指标都做成大卡片。

6. 三个独立实现的可运行原型

三种原型均为本次独立编写的HTML／CSS／JS，不是原网站截图拼装。它们接入现有HEX问题插件与实时Worker，可以切换两个问题、场景、运行共享方法、操作画面、步进、导出记录和查看已有整合实验数据。

  1. Conference / Exhibition：借鉴CoG的三种字体角色和克制游戏装饰，默认从独立展示入口进入工作区。
  2. Paper Workspace：浅色背景、干净字型、轻边界，弹性画面与右侧方法检查器并列。
  3. Canvas Focus：画面更宽，把方法设置压缩为底部控制组，适合操作和演示。

原型只演示四种共享优化方法；完整平台仍有12种方法。已有132局整合数据直接读取，未捏造展示数值。原型目录独立保存，研究与规则代码没有因样式试验改动。

7. 正式复现的代码组织

现有项目为原生ES modules，足够完成这类布局，不需要因为参考项目使用React、Vue或WASM就一并迁移。

web/design/
  tokens.css        语义色、间距、圆角、层级
  typography.css    字体资源与字型角色
  layouts.css       展示页、工作台、实验页布局
web/themes/
  exhibition.js     深色展示方案
  paper.js          浅色操作方案
  canvas.js         聚焦操作方案
web/components/
  navigation / scenario-bar / inspector / playback / metric-strip
web/views/
  metro.js / skirmish.js 仍只负责问题专属画面与动作

这是一份建议的后续结构，不表示上述目录已经被写入正式生产页面。当前三个原型已经给出可运行的版式实现。

设计令牌应使用语义名称，如surface/ink/muted/border/accent，同时区分font-body/font-data/font-display。避免在每个问题的视图里复制同一套导航、按钮和表格样式。主题切换不应触发环境重置或改变算法结果。

8. 原项目复用的实际成本

类型 代表对象 适合的复现方式
静态或小型前端 2048、Elevator Saga、Flexbox Froggy 阅读HTML和主样式，提取布局原则；仍检查版本与素材许可
复杂前端／服务端平台 Lichess、keybr、Monkeytype 借鉴布局和主题组织，不以整仓构建作为换皮的前提
图形编辑器 Excalidraw、Piskel、Squoosh 参考画布、工具和检查器的组织，将功能映射到自身组件
专用引擎或资源流水线 shapez、Sandspiel 学习HUD与画面分层，避免无必要地迁移引擎依赖
自定义许可或商业页面 tldraw、Little Alchemy 2、CoG网页 视觉与交互参考，独立实现；具体素材和代码另核许可

许可已按实际根文件核验：例如A Dark Room与CSS Diner为MPL-2.0，shapez与Monkeytype为GPL-3.0，不能按第三方汇总统称MIT。字体许可与项目代码许可也应分开。来源样本作为研究资料保存，未混入HEX运行代码。

9. 实现顺序与验收

建议顺序是：字体与令牌 → 紧凑导航和工具栏 → 工作区比例 → 方法检查器 → 实验表格 → 首页装饰。先改善使用空间和阅读层次，再补游戏氛围。

验收时重点检查：

  • 桌面常用尺寸下，场景、画面、开始／暂停／步进易于找到；移动端不发生整页横向溢出。
  • 地铁线路、单位选中态、警报和阵营仍能辨识。
  • 主题和布局切换保持当前问题、种子与状态，视觉改变不改变仿真。
  • 主要文字对比度足够，键盘焦点可见；减少动画偏好得到尊重。
  • 字体在本地加载，页面无外部字体服务依赖；数据列等宽对齐。
  • 正式集成后重新验证两个问题的操作、12方法适用性、结果导出与回放。

最终建议：CoG 2027负责“平台气质”，Excalidraw／Lichess负责“操作空间”，Elevator Saga负责“问题与方法的关系”。 这比整套照搬某一个网站，更能适配你当前的通用研究平台。
